## 114-Q029

### Question

無線 Power Saving 的典型做法(以 Wi-Fi 為例)，未涉及下列何者？

- A. STP BPDU 省電
- B. 以 TIM/Beacon 引導喚醒接收
- C. 以 ARP 抑制睡眠
- D. TWT(Target Wake Time)或 Legacy PS(PS-Poll)

### Question type

分類/反向選擇題：判斷哪些機制屬於 Wi-Fi 省電，找出「未涉及」者。

### Source packet

- Source: `src/modules/examGroups/aGroup/data/years/114.ts` Q029；review baseline: `114ReviewedAnalyses.ts` key `29`

- Accepted answer: A
- answerVerification: `verified`

- Tags: `networking`, `wifi`, `power-saving`, `802.11`
- sourceRef: `114.pdf`, page 3, extractionStatus `needs-review`

### Potential novice blockers

- 不知道 Wi-Fi 省電的核心不是「讓 AP 省電」，而是讓無線站台少開接收器、少被不必要喚醒。
- 會把所有 Layer 2 控制訊息都歸成 Wi-Fi 省電，例如把 STP BPDU 誤認為 802.11 機制。
- 不熟 Beacon/TIM、PS-Poll、TWT、ARP suppression 這些名詞各自扮演的角色。
- 題幹問「未涉及」，新手容易反向判斷失誤。

### Core terms

- Wi-Fi power saving
- Beacon/TIM
- ARP suppression / ARP offload
- TWT(Target Wake Time)
- Legacy PS / PS-Poll
- STP BPDU

### Beginner explanation

Wi-Fi power saving 要解決的問題是：無線裝置如果一直開著接收器等待封包，耗電會很快。省電模式讓站台大多數時間可以睡眠，只在 AP 通知或約定的時間醒來檢查資料。

Beacon/TIM 是 AP 在週期性 Beacon 中提示「哪些睡眠站台有資料等著收」；Legacy PS/PS-Poll 是睡眠站台醒來後向 AP 要資料的舊式流程；TWT 則是約定更精確的醒來時間。ARP suppression/offload 的教學重點是減少廣播 ARP 造成裝置被喚醒的機會。

STP BPDU 則屬於交換器/橋接器用來避免 Layer 2 迴圈的控制訊息，目標不是協調 Wi-Fi 睡眠站台的喚醒或取資料。因此本題找「未涉及」時，應選 A。

1. 先標記題幹關鍵字「未涉及」，答案要找非 Wi-Fi 省電做法。
2. 檢查 B：Beacon/TIM 是 AP 通知睡眠站台是否有緩衝資料的典型機制，屬於 Wi-Fi 省電。
3. 檢查 D：TWT 與 Legacy PS/PS-Poll 都與安排醒來時間或取回資料有關，屬於 Wi-Fi 省電。
4. 檢查 C：ARP suppression/offload 可減少廣播 ARP 造成的喚醒，可歸入省電相關做法。
5. 檢查 A：STP BPDU 是交換網路生成樹協定訊息，和睡眠站台、Beacon/TIM、PS-Poll、TWT 無關。
6. 因此答案選 A。

- A: 正確。STP BPDU 的目的在避免交換網路迴圈，不是 Wi-Fi power saving。
- B: 錯誤。Beacon/TIM 是 802.11 省電中提示睡眠站台是否有待收資料的機制。
- C: 錯誤。ARP suppression/offload 可減少裝置因 ARP 廣播而醒來，和降低耗電有關。
- D: 錯誤。TWT、Legacy PS、PS-Poll 都與醒來排程或醒來後取資料有關。

### Key takeaways

- Wi-Fi 省電的核心是讓站台少醒來、按需要醒來。
- Beacon/TIM、PS-Poll、TWT 都是典型 802.11 省電相關機制。
- ARP suppression/offload 的省電價值在於減少廣播封包造成的不必要喚醒。

## 114-Q030

### Question

MTU=1500B、IP Header=20B，若發送 2300B 負載，會產生幾個 IP 片段？

- A. 2
- B. 3
- C. 4
- D. 5

### Question type

### Source packet

- Source: `src/modules/examGroups/aGroup/data/years/114.ts` Q030；review baseline: `114ReviewedAnalyses.ts` key `30`
- Topic: IP 分片
- Accepted answer: A
- answerVerification: `verified`
- answerNote: `null`
- Tags: `networking`, `ip`, `fragmentation`, `mtu`
- sourceRef: `114.pdf`, page 3, extractionStatus `needs-review`

### Potential novice blockers

- 容易把 MTU 誤以為只包含 payload，忘記 MTU 包含 IP header。
- 不知道每個 fragment 都會有自己的 IP header。
- 不熟 IPv4 fragment 除最後一片外 payload 通常需符合 8-byte boundary。
- 可能直接算 `2300 / 1500`，忽略題目說的是 2300B 負載。

### Core terms

- IPv4 fragmentation
- MTU
- IP header
- payload
- 8-byte boundary

### Beginner explanation

IPv4 fragmentation 要解決的問題是：封包太大時，下一段鏈路無法一次承載，就要拆成多個 IP 片段。MTU 是鏈路上單一封包可承載的總大小，包含 IP header，所以每片能放的資料量要先用 MTU 扣掉 header。

本題 MTU 是 1500B，IP header 是 20B，因此每片最多能放的 payload 是 `1500 - 20 = 1480B`。題目說要送 2300B 負載，所以第一片可放 1480B，剩下 `2300 - 1480 = 820B`。

剩餘 820B 加上第二片自己的 20B header，總長 840B，沒有超過 MTU 1500B，因此第二片就能放完。第一片 payload 1480B 也可被 8 整除，符合非最後片段常見對齊規則，所以總共 2 個片段。

### Teaching tables

既有 reviewed analysis 已符合新手教學標準；建議新增一張公式/流程對照表，因本題是計算題，表格能把「每片都有 header」視覺化。

| 片段 | Payload 大小 | Header 大小 | 片段總長 | 判斷 |
| --- | ---: | ---: | ---: | --- |
| 第 1 片 | 1480B | 20B | 1500B | 放滿 MTU；1480 可被 8 整除，合法。 |
| 第 2 片 | 820B | 20B | 840B | 小於 MTU，可放完剩餘負載。 |

### Solving steps

1. 確認題目給的 2300B 是 payload，不包含 IP header。
2. 每個片段都需要 IP header，所以每片 payload 上限是 `1500 - 20 = 1480B`。
3. 第一片放 1480B，剩餘 payload 是 `2300 - 1480 = 820B`。
4. 檢查 8-byte boundary：1480 可被 8 整除，可作為非最後片段 payload。
5. 第二片放 820B payload，加上 20B header 後總長 840B，小於 1500B。
6. 因此總片段數是 2，答案選 A。

### Option explanations

- A: 正確。2300B payload 可拆成 1480B 與 820B 兩段，共 2 個 IP 片段。
- B: 錯誤。需要 3 片代表單片可承載負載遠小於本題的 1480B。
- C: 錯誤。4 片過多，表示沒有正確扣除 MTU 可承載量。
- D: 錯誤。5 片更不符合 1480B 的單片負載上限。

### Key takeaways

- MTU 包含 header；計算 fragment payload 時要先扣掉 IP header。
- 每個 fragment 都有自己的 IP header。
- 除最後一片外，IPv4 fragment payload 長度通常要符合 8-byte boundary。
- 常見陷阱是直接用 payload 除以 MTU，或忘記最後一片只要能放下剩餘資料即可。

- Novice Reviewer: pass。既有解析已說明 MTU、header、payload 與套用流程。

## 114-Q031

### Question

若設定 DF=1 而路徑 MTU 低於封包大小，PMTUD 的關鍵回饋機制為何？

- A. TCP RST
- B. 路由器回 ICMP Time Exceeded
- C. 路由器回 ICMP Fragmentation Needed
- D. ARP

### Question type

機制辨識題：PMTUD 在 DF 封包過大時的錯誤回饋。

### Source packet

- Source: `src/modules/examGroups/aGroup/data/years/114.ts` Q031；review baseline: `114ReviewedAnalyses.ts` key `31`
- Topic: PMTUD
- Accepted answer: C
- answerVerification: `verified`
- answerNote: `null`
- Tags: `networking`, `icmp`, `pmtud`, `mtu`
- sourceRef: `114.pdf`, page 3, extractionStatus `needs-review`

### Potential novice blockers

- 不知道 DF 是 Do Not Fragment，代表路由器不能分片。
- 不理解 Path MTU 是整條路徑中最小可通過封包大小。
- 容易把 ICMP Time Exceeded 和 Fragmentation Needed 混淆。
- 不知道 PMTUD 是來源端靠錯誤回饋調小封包，而不是中途路由器自動修好。

### Core terms

- PMTUD(Path MTU Discovery)
- DF bit
- ICMP Fragmentation Needed
- Path MTU
- 瓶頸 MTU

### Beginner explanation

PMTUD 的目的，是讓來源端找出整條路徑上能安全通過的最大封包大小。端到端路徑會經過多段鏈路，每段 MTU 可能不同；其中最小的那段會限制整條路徑，稱為 Path MTU 或瓶頸 MTU。

DF=1 代表 Do Not Fragment，中途路由器不能替封包分片。當路由器發現下一段鏈路 MTU 比封包小時，它不能送原封包，也不能切小，只能丟棄並回報錯誤。

PMTUD 的關鍵回饋是 ICMP Fragmentation Needed。來源端收到後才知道封包太大，接著降低封包大小或 TCP MSS。Time Exceeded 是 TTL 歸零常見於 traceroute，不是 MTU 太小的回饋。

### Teaching tables

既有 reviewed analysis 已符合新手教學標準；不需要新增表格。這題判斷鏈很短，段落與 solving steps 已能清楚呈現「DF=1、封包過大、路由器回 ICMP Fragmentation Needed」的流程。

### Solving steps

1. 看到 DF=1，先判斷中途路由器不得分片。
2. 題目說路徑 MTU 低於封包大小，代表某段鏈路出現瓶頸 MTU。
3. 封包太大又不能分片時，路由器必須丟棄封包並回報 ICMP Fragmentation Needed。
4. 來源端收到回饋後，調小後續封包大小或 TCP MSS，形成 PMTUD 回饋迴路。
5. 排除 Time Exceeded，因為它處理 TTL 歸零；排除 TCP RST 與 ARP，因為它們不回報路徑 MTU。
6. 因此答案選 C。

### Option explanations

- A: TCP RST 是 TCP 連線重設，不是路由器通知 MTU 太小的機制。
- B: ICMP Time Exceeded 主要用於 TTL 歸零，例如 traceroute，不是 PMTUD 核心回饋。
- C: 正確。ICMP Fragmentation Needed 表示 DF 封包太大、路由器不能分片，用來通知來源端調整大小。
- D: ARP 只在區域網路解析 IP 對 MAC 位址，與 Path MTU 探測無關。

### Key takeaways

- DF=1 代表中途路由器不得分片。
- PMTUD 靠 ICMP Fragmentation Needed 得知瓶頸 MTU。
- 來源端收到回饋後要降低封包大小或 TCP MSS。
- 常見陷阱是把 ICMP Time Exceeded、TCP RST 或 ARP 當成 MTU 探測回饋。

### Question

有關 ping 與 traceroute 的主要差異，下列何者正確？

- A. 前者測路徑、後者測延遲
- B. 前者測可達性，後者推路徑節點
- C. 前者用 TCP，後者用 UDP
- D. 前者應用層，後者傳輸層

### Question type

比較題：網路診斷工具目的與基本機制比較。

### Source packet

- Source: `src/modules/examGroups/aGroup/data/years/114.ts` Q032；review baseline: `114ReviewedAnalyses.ts` key `32`
- Topic: ping 與 traceroute
- Accepted answer: B
- answerVerification: `verified`

### Potential novice blockers

- 以為 ping 和 traceroute 都只是「測網路通不通」。
- 不知道 ping 的重點是可達性與 RTT，不是列出沿途路由器。
- 不理解 traceroute 利用 TTL 遞增與 ICMP Time Exceeded 推估路徑節點。

### Core terms

- ping
- traceroute
- ICMP Echo
- TTL
- RTT(round-trip time)

### Beginner explanation

ping 的核心問題是「我能不能到達目標主機」。典型 ping 送出 ICMP Echo Request，若目標回 ICMP Echo Reply，就表示封包至少能往返，並可估算 RTT。

traceroute 的核心問題是「封包大概經過哪些節點」。它利用 TTL 每經過一台路由器就減 1 的規則，讓 TTL 從 1、2、3 逐步增加；當 TTL 歸零時，沿途路由器會回 ICMP Time Exceeded，traceroute 就能推估每一跳。

所以 ping 主要測可達性與延遲，traceroute 主要推路徑節點。不同系統的 traceroute 可用 UDP、ICMP 或 TCP 探測，不能只用封包協定名稱來區分。

### Teaching tables

既有 reviewed analysis 已符合新手教學標準；建議新增比較表，因本題直接比較 ping 與 traceroute，表格能讓工具目的、機制與常見陷阱更容易掃讀。

| --- | --- | --- | --- |
| ping | 測目標是否可達、估算 RTT | ICMP Echo Request/Reply | 不是列出路徑節點。 |
| traceroute | 推估封包經過的沿途節點 | TTL 遞增，沿途回 ICMP Time Exceeded | 探測封包型態可依系統不同，不宜只背 UDP/TCP。 |

### Solving steps

1. 先看 ping：常用 ICMP Echo Request/Reply，重點是目標是否回應與 RTT。
2. 再看 traceroute：操控 TTL，讓沿途路由器逐跳回應，藉此推估路徑節點。
3. 檢查 A：把 ping 說成測路徑、traceroute 說成測延遲，方向相反。
4. 檢查 B：前者測可達性，後者推路徑節點，符合核心目的。
5. 檢查 C：ping 通常用 ICMP，traceroute 可用 UDP、ICMP 或 TCP，不能簡化成前者 TCP 後者 UDP。
6. 檢查 D：兩者不能用應用層/傳輸層這種說法區分。
7. 因此答案選 B。

### Option explanations

- A: 錯誤。ping 不是用來列出路徑，traceroute 才是推估路徑節點。
- B: 正確。ping 測可達性，traceroute 推估沿途節點。
- C: 錯誤。ping 通常用 ICMP；traceroute 依系統可用 UDP、ICMP 或 TCP。
- D: 錯誤。兩者不是用應用層與傳輸層來區分。

### Key takeaways

- ping 重點是可達性與 RTT。
- traceroute 重點是用 TTL 遞增觀察路徑上的每一跳。
- traceroute 探測封包型態會依作業系統與參數不同。
- 常見陷阱是把工具使用的封包型態當成主要差異；本題要先看目的。

乙太網路 CSMA/CD 在碰撞後避免再次碰撞的機制為何？

- B. 令牌傳遞
- C. TDMA

### Question type

### Source packet

- Source: `src/modules/examGroups/aGroup/data/years/114.ts` Q033；review baseline: `114ReviewedAnalyses.ts` key `33`
- Topic: CSMA/CD
- Accepted answer: A
- answerVerification: `verified`

### Potential novice blockers

- 不熟 CSMA/CD 的情境是傳統共享式半雙工 Ethernet。
- 看到「避免碰撞」就誤選 Wi-Fi 的 RTS/CTS。
- 不理解二元指數退避不是固定等待，而是碰撞越多，隨機等待範圍越大。
- 會把 token passing、TDMA、RTS/CTS 這些不同媒體存取方法混成同一類。

### Core terms

- CSMA/CD
- collision
- binary exponential backoff
- half-duplex Ethernet

### Beginner explanation

CSMA/CD 是傳統共享式半雙工 Ethernet 的媒體存取方法。多台設備共用同一媒介時，如果兩台同時送，就會發生 collision。CSMA/CD 代表先聽媒介、多人存取，並在傳送時偵測碰撞。

碰撞發生後，所有設備不能立刻一起重送，否則很可能再次碰撞。二元指數退避的做法是讓設備在重送前隨機等待，而且碰撞次數越多，可能等待的範圍越大。

本題限定 CSMA/CD 碰撞後機制，因此答案是二元指數退避。令牌傳遞、TDMA、RTS/CTS 分別屬於其他媒體存取或無線協調方法。

### Teaching tables

### Solving steps

### Potential novice blockers

- 不理解 hidden node 是「兩個站彼此聽不到，但都能干擾同一 AP」。
- 會把 Wi-Fi 的 CSMA/CA 與有線 Ethernet 的 CSMA/CD 混淆。
- 不知道 RTS、CTS、ACK 每個訊框的目的。

### Core terms

- hidden node
- RTS(Request To Send)
- CTS(Clear To Send)
- ACK
- CSMA/CA
- NAV

### Beginner explanation

隱藏節點問題發生在兩個無線站彼此聽不到對方訊號，但都能送到同一個 AP。A 站以為空中媒介是空的，B 站也以為是空的，兩者同時傳給 AP 時，就可能在 AP 端碰撞。

RTS/CTS 的目的，是在真正傳資料前先預約空中媒介。傳送端送 RTS，AP 或接收端回 CTS，其他聽到 CTS 或相關控制訊框的站台會依 NAV 保留時間暫停傳送。資料送完後，ACK 用來確認接收成功。

本題問常用流程，所以答案是 RTS/CTS/ACK。CSMA/CD 是有線乙太網路的碰撞偵測；Wi-Fi 很難一邊傳一邊偵測碰撞，因此採 CSMA/CA，重點是盡量避免碰撞。

### Teaching tables

既有 reviewed analysis 已符合新手教學標準；建議新增流程表，因題幹問「流程」，表格能把 RTS、CTS、ACK 的順序與目的拆清楚。

| 步驟 | 訊框/動作 | 新手理解 |
| --- | --- | --- |
| 1 | RTS | 傳送端先請求傳送，像是先舉手預約。 |
| 2 | CTS | AP/接收端回覆可傳送，其他站台聽到後暫停。 |
| 3 | Data | 傳送端在預約時間內送資料。 |
| 4 | ACK | 接收端確認資料收到。 |

### Solving steps

1. 先辨識隱藏節點：兩個站彼此聽不到，但都能影響同一 AP。
2. 因為彼此聽不到，只靠一般載波感測不一定知道對方要傳，所以需要先預約空中媒介。
3. RTS 先提出傳送請求，CTS 回覆允許，周邊站台聽到後暫停，降低同時送到 AP 的機率。
4. ACK 在資料傳輸後確認接收成功，形成 RTS/CTS/ACK 流程。
5. 排除 CSMA/CD，因為 Wi-Fi 使用 CSMA/CA 避免碰撞，不是有線半雙工 Ethernet 的碰撞偵測。
6. 因此答案選 A。

### Option explanations

- A: 正確。RTS/CTS 透過預約媒介降低隱藏節點同時傳送的機率，ACK 確認資料成功接收。
- B: 錯誤。CSMA/CD 是有線 Ethernet 的碰撞偵測，Wi-Fi 無法邊傳邊有效偵測碰撞。
- C: 錯誤。令牌環是 Token Ring 的媒體存取方式，不是 Wi-Fi hidden node 解法。
- D: 錯誤。MIMO 可提升傳輸容量與可靠性，但不是典型的隱藏節點控制流程。

### Key takeaways

- RTS/CTS 先預約媒介，降低同時傳送造成的碰撞。
- ACK 用來確認資料幀接收成功。
- Wi-Fi 使用 CSMA/CA 避免碰撞，不是 CSMA/CD 碰撞偵測。

### Beginner explanation

HTTP stateless 的意思是，HTTP request/response 原本是一來一回的獨立交換。伺服器收到下一個 request 時，協定本身不會自動知道「這就是剛剛登入的那個使用者」。

Cookie 的規則是伺服器可在 response 要瀏覽器保存一小段資料；瀏覽器之後對同一網站發出 request 時，會把 Cookie 帶回去。實務上 Cookie 常放 session id，伺服器再用這個 id 查到使用者登入狀態、購物車或偏好設定。
