### Beginner explanation

DNS 查詢可以想成「逐層問路」。DNS 命名空間有 root、TLD，例如 `.com`、`.tw`，以及真正管理某個網域的 authoritative server。查詢端不一定一開始就問到知道最終答案的伺服器，因此需要逐層找。

Iterative query 的規則是：被問到的 DNS server 不替你一路查到底，而是回 referral，也就是「我不知道最終答案，但你下一步可以問誰」。查詢端拿到 referral 後，再去問下一層，逐步從 root 問到 TLD，再問到 authoritative server。

Recursive query 則是另一種責任分工：查詢端把工作交給 resolver，要求 resolver 代查到底，最後只把結果交回來。本題的重點不是 TCP 53，也不是每次回覆都已經是權威答案，而是「客戶端逐層查、伺服器回下一步」。

### Beginner explanation

Open Resolver 的常見風險包含 DNS amplification：攻擊者偽造受害者來源位址，讓 resolver 把較大的 DNS 回應送到受害者，形成放大 DDoS。它也可能洩漏查詢紀錄、快取線索，或被拿來探測內部名稱。

### Key takeaways

### Core terms

- DDoS

### Beginner explanation

DDoS 是用大量流量塞爆目標或路徑。防護時，第一個目標常是避免核心網路、其他客戶或關鍵服務被一起拖垮，因此要先處理流量流向。

Blackholing 是把特定惡意流量或目的路由導向黑洞，效果偏向丟棄流量。Sinkholing 則是把惡意流量導到受控位置，讓防護方可以收容、觀察、分析或阻斷。兩者共同點都是 traffic diversion：把攻擊流量導走、丟棄或收容。

所以本題主要目的不是加密內容、建立登入控管，也不是提升帳號驗證強度，而是將惡意流量導走或收容解析。

### Beginner explanation

Load balancer 負責把前端收到的請求分給後端伺服器。分派演算法回答的是「下一個請求要給誰」，不是產品支不支援 SSL、L7 routing 或健康檢查。

Round Robin 是輪流分派，例如 A、B、C、A、B、C，通常假設後端能力差不多。Weighted Round Robin 則加入 weight 權重，例如 A 權重 3、B 權重 1，就讓 A 依比例拿到更多請求，反映硬體容量或可承受負載不同。

### Option explanations

- A: 對。Weighted Round Robin 會依權重分派，Round Robin 不會。

### Key takeaways

- Weighted Round Robin 是依 weight 比例分派。
- 權重常用來反映後端伺服器容量差異。

### Question type

### Potential novice blockers

### Core terms

- Session Stickiness
- session affinity
- load balancer
- stateful backend

### Beginner explanation

在負載平衡環境中，同一個網站後面可能有多台後端伺服器。Load balancer 會把每次請求分派給其中一台。如果應用是 stateful backend，也就是登入狀態、購物車或暫存資料只存在某一台後端，使用者下一個請求被分到另一台就可能讀不到 session。

Session Stickiness 又稱 session affinity，做法是讓同一使用者在一段時間內持續被導到同一台後端。常見實作包含 load balancer cookie、source IP hash 或其他黏著策略。

本題的描述是避免會話在多台伺服器間漂移，所以答案是 Session Stickiness。HSTS、HPKP、OCSP Stapling 都是 HTTPS 或憑證相關安全機制，不決定使用者要被導到哪一台後端。

### Teaching tables

Decision: 不需要新增 `teachingTables`。四個選項分屬 session 分派與 HTTPS/憑證機制，現有 option explanations 已足夠清楚。

### Solving steps

1. 先抓題幹「多台伺服器間漂移」與「使用者會話異常」。
2. 這代表使用者請求被 load balancer 分到不同後端，導致 session 找不到。
3. Session Stickiness 可讓同一使用者黏到同一後端。
4. HSTS 只要求瀏覽器使用 HTTPS。
5. HPKP 與 OCSP Stapling 是憑證相關機制，不處理後端分派。
6. 因此答案選 D。

### Option explanations

- A: 錯。HSTS 要求瀏覽器使用 HTTPS，不能控制後端伺服器分派。

### Core terms

- SQL Injection

### Beginner explanation

SQL Injection 的問題通常來自字串拼接。程式若把使用者輸入直接拼到 SQL 裡，例如 `WHERE name = '<輸入>'`，攻擊者就可能輸入引號、OR 條件或註解符號，讓資料庫把輸入當成 SQL 指令的一部分。

Prepared Statements 的核心是 code/data separation：先固定 SQL 結構，例如 `WHERE name = ?`，再把使用者輸入用參數綁定進去。資料庫會把參數當成資料值，而不是新的 SQL 語法片段。

因此關鍵不是把輸入轉 16 進位或 Base64，也不是用 Try/Catch 捕捉錯誤，而是讓 SQL 指令結構與資料值分離。

### Teaching tables

Decision: 不必強制新增 `teachingTables`；現有說明已足夠。若主代理想讓新手更快比較，可加入以下流程/對照表。

| 做法 | 資料庫如何看待使用者輸入 | 是否能作為主要防線 |
| --- | --- | --- |
| 字串拼接 SQL | 可能被當成 SQL 語法 | 否 |
| 16 進位/Base64 | 只是改變表示方式，解碼後仍可能拼接 | 否 |
| Try/Catch | 錯誤發生後才處理例外 | 否 |
| Prepared Statements | 參數被當成資料值 | 是 |

### Solving steps

1. 先辨認題目問 SQL Injection 的防護核心。
2. Injection 成立原因是使用者輸入被拼進 SQL 結構，可能變成可執行語法。
3. Prepared Statements 先固定 SQL 結構，再用參數綁定資料。
4. A 與 C 只是編碼或表示方式，不保證阻止 SQL 語意。
5. B 是例外處理，不會阻止惡意 SQL 被組成或執行。
6. 因此答案選 D。

### Option explanations

- A: 錯。轉成 16 進位只是表示方式改變，若仍拼接 SQL，風險仍在。
- B: 錯。Try/Catch 只能捕捉例外，不能防止 injection。
- C: 錯。Base64 是編碼，不是安全邊界。
- D: 對。參數化查詢讓 SQL 結構與資料值分離，是 prepared statements 的關鍵。

### Key takeaways

- SQL Injection 的核心風險是資料被當成指令。
- Prepared Statements 用參數化查詢達成 code/data separation。
- 編碼與例外處理不能取代參數化查詢。
- 防護要看資料庫如何解析 SQL 與參數，而不是輸入看起來是否被處理過。

### Beginner explanation

IAM（Identity and Access Management）是「管理誰可以進來、進來後可以做什麼」的整體範圍。它包含身分建立、authentication 驗證、authorization 授權、帳號生命週期、政策與稽核等面向。

RBAC（Role-Based Access Control）是 authorization 的一種模型。它先定義 role 角色，例如管理員、審核者、一般使用者，再把權限掛在角色上；使用者取得某個角色後，就得到該角色的權限。

所以包含關係是 RBAC 屬於 IAM 的一種授權方式，不是 IAM 屬於 RBAC，也不是兩者相等。
